## Feature claim

From the baseline opening Vincent selects an offered SecureTribute target/method, then himself or
Tommy, reviews the plan, and confirms once. Direct delegation creates one operation with Vincent as
owner and Tommy as initial executor, without a temporary personal start. An owner already executing
work may commission a free known subordinate; execution capacity and supervision are separate.
Qualified autonomous actors must reach the same commissioning path now, not eventually.

## Implementation delivered

Implemented by Codex in `codex/milestone-031-commission-job`, based on `ae4e465` (Milestone 030
closure), whose implementation parent is `5874077`. The implementation commit is the commit that
adds this archive; no self-referential hash or independent acceptance is asserted here.

- `Commissioning` caches the executor evaluation after a retained SecureTribute leaf. Retention
  filters existing eligibility and salience, orders by salience then the sum of existing delegation
  relationship/capability considerations, breaks ties by candidate id, and keeps at most five
  delegates. Eligible self is added independently. `Utility.DelegationConsiderations` is shared by
  retention and full evaluation, with the existing coefficients and capability ladder unchanged.
  Only retained alternatives receive full scoring/noise. A keyed `ForOccasion` stream gives each
  decision/leaf stable draws without consuming the first-stage stream or world counters. Cache hits
  return the same evaluation; a caller cannot replace the retained leaf's fields through its id.
- `SimulationSession` holds the unresolved decision, selected leaf and optional executor. Existing
  `Choose` commands record leaf, executor, back and confirmation inputs. `PersistentSession` needs
  no new command type, schema, serialization system or delayed command. Real Godot buttons expose
  the same draft. Confirmation calls the shared `Pipeline.Resolve`; automatic resolution prepares
  and evaluates the identical executor alternatives now.
- `Commit` validates before writing and creates the initial owner/executor association directly.
  It retains assignment, deadline, ordered method and responsibility, creates the usual commitments,
  and schedules the original strategy step/review paths. There is no temporary personal start or
  replacement of the owner's existing execution. Owner review, reassignment, cancellation and
  executor control continue through their existing paths.
- `AssignmentBriefing` extracts the existing bounded target assessment and receipt effects. Initial
  delegation captures the target refusal and held affirmative assessment at confirmation, retaining
  the issuer's stance, confidence and claimed basis. Ordinary recipient receipt can agree, conflict,
  or revise; the initial packet is not reread from later issuer beliefs.
- Executor learning acquired during a strategy advance keeps that operation's owner/local identity.
  A report carries attribution only for actually asserted claims whose current held record is still
  the recorded acquisition. The recipient stores the account only on delivery. Matching a target,
  any report by the same person, or private advancement alone cannot update the owner's operation
  status. A later unrelated source for the same claim loses the old attribution. Existing reporting
  vocabulary and ordinary receipt-triggered reviews are preserved.
- The planning text is a static multi-day expectation. The operation card shows the owner's ordered
  method and an attributed account/no-account status, while personal progress remains executor-only.
  Staffing explanations name only known people and the owner's own orders. Existing completion
  bookkeeping remains: the fact that an operation ended is visible as settled by milestone 026;
  private reasons for its ending are not thereby disclosed (`PlayerOccasion`'s existing boundary).
- Developer decision traces now include the separate executor alternatives and selected executor.
  The chosen-action signature and replay comparators include the new decision and attribution state.
  No fixture, personality, capability weight, resistance, interval, calendar or RNG algorithm was tuned.

### Deliberate fault checks

Each mutation was applied independently, required a failing relevant test, and was restored before
final verification. All twelve were detected:

1. Drop the initial delegated executor, creating a personal start.
2. Restrict automatic executor choice to self.
3. Discard the cached executor evaluation and prepare it again.
4. Retain a sixth delegate in addition to protected self.
5. Ignore held capability judgments when retaining delegates.
6. Append hidden target resistance to the planning expectation.
7. Copy the issuer's broader cognition into the initial briefing.
8. Treat an account for another operation as this operation's status.
9. Show the delegate's private live method to the owner.
10. Reschedule execution when an owner leaves orders unchanged.
11. Omit draft choices from the existing persistence input log.
12. Multiply first-stage operation candidates with executor-shaped copies.

Objective subordinate skill is structurally unavailable to the retention/scoring helper, which
receives actor view, perceived situation and existing psychology only. This boundary was inspected;
no claim is made that a fabricated world-truth skill lookup was itself mutation-tested. Information
boundary tests additionally cover unrelated reports, wrong recipients, later source changes, hidden
method/failure/phase, unknown work, and authoritative commit-time eligibility changes.
